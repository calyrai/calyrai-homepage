Calyr Knowledge Architecture

Calyr Ecosystem Overview

SQL organizes data. Calyr organizes knowledge: typed objects, explicit semantic links, immutable versions, and artifact-level traceability in one operational system.

Core ClaimNexus subsumes table logic while preserving scientific semantics and provenance.
NeedWithout this layer, data, discussion, models, and outputs fragment and lose interpretability.

Why Calyr is necessary

Scientific workflows do not fail because of missing files, they fail because context gets severed. Calyr keeps experiments, model states, literature claims, and published artifacts inside one linked object space so reasoning survives across iterations.

Calyr.Nexus is therefore a typed, relational, graph-extended, versioned object system: you do not overwrite state, you evolve it with lineage.

How modules relate

Nexus routes information; eval, okto, and literature enrich the shared object layer.

Design principles

  • One source of truth: every run, model, and result is registered once and referenced everywhere.
  • Local first: heavy compute stays local; lightweight surfaces stay portable.
  • Composable: modules can run standalone or chained without workflow lock-in.

FAIR data requirement

FAIR is treated as system behavior, not a documentation afterthought: objects are Findable by stable IDs, Accessible via reproducible paths, Interoperable through typed contracts, and Reusable through provenance and lineage.

This is why Nexus stores object metadata, semantic relations, immutable versions, and artifacts together in one execution model.
