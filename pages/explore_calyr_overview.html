Calyr Knowledge Architecture

Calyr Ecosystem Overview

SQL organizes rows. Calyr organizes scientific decisions: typed objects, explicit semantic links, immutable versions, and artifact-level traceability in one operating layer.

Value PropositionCalyr turns disconnected files into a governed knowledge graph that remains interpretable under iteration.
Why It MattersWhen model context is persistent, teams spend less time reconstructing history and more time making reliable decisions.

Higher Signal

Each result is connected to assumptions, method, and provenance rather than stored as an isolated output.

Lower Friction

Cross-module handoffs are object-linked, so transitions from analysis to publication do not lose context.

Stronger Reuse

Versioned objects allow safe iteration: new states are added without destroying scientific lineage.

Why Calyr is necessary

Scientific workflows rarely fail from missing files alone; they fail when context breaks between data, models, interpretation, and publication. Calyr keeps experiments, model states, literature claims, and deliverables in one linked object space so reasoning survives every iteration.

Calyr.Nexus is a typed, relational, graph-extended, versioned object system: state is never overwritten, it is evolved with lineage.

How modules relate

Nexus routes information; eval, okto, and literature enrich the shared object layer.

Design principles

  • One source of truth: every run, model, claim, and result is registered once and referenced everywhere.
  • Local first: heavy compute stays local; lightweight interfaces stay portable.
  • Composable: modules run standalone or chained without workflow lock-in.

FAIR data requirement

FAIR is system behavior, not a documentation afterthought: objects are Findable by stable IDs, Accessible via reproducible paths, Interoperable through typed contracts, and Reusable through provenance and lineage.

That is why Nexus stores metadata, semantic relations, immutable versions, and artifacts together in one execution model.
