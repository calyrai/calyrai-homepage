## Page calyr-business-model
Organizing knowledge to enable innovation.

Most digital companies build software.

Most software companies build interfaces.

Calyr.aí builds knowledge structures from which interfaces, tools, and innovations emerge.

The primary product is not software. The primary product is the organization, compression, relation, and projection of knowledge.

## Executive Summary

Calyr.aí starts from a different first principle than a classical software or SaaS company. It treats knowledge topology as the core asset and software as one projection of that asset. Interfaces, AI outputs, glyph systems, workflows, papers, and tools are downstream expressions of an underlying semantic structure.

The business therefore focuses on designing, constructing, and operating knowledge architectures that make innovation less accidental and more systematic.

## Problem

Modern organizations continuously generate documents, papers, data, models, code, reports, workflows, and AI outputs.

The information exists. The structure does not.

- Knowledge becomes fragmented.
- Expertise becomes isolated.
- Innovation becomes accidental.
- Interfaces become increasingly complex.

Organizations spend enormous resources creating information while losing the relations between information.

## Hypothesis

Knowledge is inherently relational. Innovation emerges when previously disconnected concepts become connected.

Traditional product logic often assumes the following sequence: software, then features, then innovation.

Calyr.aí reverses that sequence. It starts with knowledge, makes relations explicit, organizes them into an atlas, derives tools from that atlas, and creates the conditions for innovation.

## Core Product

Calyr.aí creates semantic knowledge structures.

The atomic unit is not a page. The atomic unit is a knowledge object.

- Papers
- Concepts
- Models
- Workflows
- Experimental results
- Visualizations
- Code fragments

Each object exists within a larger network of relations. Value comes from the system of relations rather than from isolated files.

## Atlas

The Atlas is the primary product.

It is a living topology of knowledge that organizes concepts, papers, projects, methods, results, and models into a connected semantic landscape.

As new knowledge is added, the atlas evolves. It is not a static repository. It is a dynamic structural layer that can continuously generate new views, new navigation paths, and new operational tools.

## Interface Philosophy

Traditional software is often designed from the interface downward. Content is fitted into predetermined screens.

Calyr.aí works in the opposite direction. Knowledge is organized first, relations are mapped second, an atlas is formed third, and the interface emerges from that structure.

This reduces the need to manually design every surface in isolation and creates a more coherent environment for navigation and discovery.

## Glyph Interface

Knowledge is represented through semantic glyphs.

A glyph is a compressed representation of a concept. In science, equivalent compression systems already exist in chemical structures, mathematical notation, and Feynman diagrams.

Glyphs act as visual compression, navigation objects, knowledge markers, and cognitive tools.

## Value Proposition

Calyr.aí helps organizations organize complex knowledge, discover hidden relations, navigate large information spaces, build reusable knowledge structures, and accelerate innovation.

The objective is not information storage. The objective is knowledge discovery.

## Page calyr-page-design
Page Design

## Design Principle

The page system is source-first.

Markdown defines canonical content.

YAML defines projection metadata such as tile behavior, links, and page outputs.

The renderer composes both into stable HTML while preserving the existing visual layout.

## Object-Oriented Structure

The homepage architecture follows an object-oriented model:

- Content objects hold text semantics.
- Page objects define projection targets.
- Renderer objects map content to concrete layout surfaces.

This separation keeps implementation extensible while preventing accidental layout drift.

## Layout Stability Rule

Design iteration must not rewrite the visible shell by default.

Changes should prefer:

- markdown content updates,
- YAML projection updates,
- renderer internals that preserve existing structure.

This keeps the current homepage recognizable while still enabling system-level evolution.

## Page calyr-engine-project-description
Engine Project Description

## Project Scope

This project defines a reusable engine-page architecture for CALYR workflows.

The first reference implementation is the AlphaFold workflow surface.

The objective is stable visual continuity with internal object-oriented reusability.

## Structural Model

The page is organized through objects rather than static HTML composition.

- CalyrPage as root abstraction
- EnginePage for runtime-specific context
- WorkflowPage for node and edge orchestration
- WorkflowCanvas for interactive graph rendering
- EnginePanel and ProjectionPanel for controls and metadata

## Workflow Stages

The baseline engine flow is represented as ordered stages:

- Sequence Input
- Model Prediction
- Structure Output
- Validation
- Projection

These stages are defined in source configuration and rendered consistently through the same layout shell.

## ASC Integration Surface

ASC integration is treated as a runtime adapter layer.

The adapter prepares submission payloads, preserves provenance, and separates execution concerns from UI concerns.

This keeps the user interface stable while enabling runtime expansion.

## Delivery Rule

No redesign is required for this project description path.

Content evolves through markdown.

Projection evolves through YAML.

Rendering evolves through object-oriented internals.
